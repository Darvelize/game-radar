# Publication

**Exécutable à partager** (profil `src/GameRadar.App/Properties/PublishProfiles/win-x64.pubxml`) : un seul `GameRadar.exe` (~22 Mo) pour Windows 64 bits, sans installer .NET.
- *Self-contained* + *single-file* + natifs Avalonia inclus (SkiaSharp, HarfBuzz : extraits dans un dossier temporaire au 1er lancement) + compression. **Trimmé** (`PublishTrimmed=true`, 49 → ~22 Mo, depuis la 1.4.0) : possible parce que tout le JSON passe par des contextes générés (pas de réflexion) et que les bindings sont compilés. **Après tout changement de paquet, de SDK ou de JSON, lancer l'exe publié** (pages clair/sombre, français/anglais, À propos, Ajouter un jeu, synchro) : les tests ne couvrent pas l'exe trimé ; si une page casse, repasser `PublishTrimmed` à `false`. Les `.pdb` natifs des paquets SkiaSharp/HarfBuzz (~105 Mo) sont retirés par la cible `RemoveNativeSymbolsFromPublish` du `.csproj`.
- Assembly `GameRadar` (espaces de noms toujours `GameRadar.App`) : les ressources du thème sont incluses par chemin relatif (`/Themes/…`), pas par `avares://<assembly>/…`, pour ne pas dépendre du nom. Version dans `<Version>` du `.csproj`.
- Icône `Assets/GameRadar.ico` (exe + fenêtre) : le tracé `IconRadar` en blanc sur un carré `#6B4EFF` aux coins arrondis, rendu nativement en 16 à 256 px par Avalonia headless puis assemblé en `.ico` (entrées PNG) ; le refaire de la même façon si le logo change.
- **Publication automatique** (GitHub Actions, `.github/workflows/`, mise en place en oct. 2026) : `ci.yml` construit et teste à chaque push et pull request (runner Windows, SDK épinglé à celui du poste : le test des notices tierces en dépend, monter les deux ensemble). `release.yml` publie : un tag `vX.Y.Z` poussé (après le commit « Release X.Y.Z », étapes 1 et 2 ci-dessous) lance les tests, le `dotnet publish`, `tools/Build-ReleaseNotes.ps1` (notes françaises puis anglaises extraites des changelogs, installation, SHA-256 : même texte que l'étape 3 faite à la main) puis l'**attestation de provenance** de l'exe (`actions/attest-build-provenance` : n'importe qui vérifie avec `gh attestation verify GameRadar.exe -R Darvelize/game-radar`) et `gh release create` dans ce même dépôt. **Il refuse** un tag différent de `<Version>`, une section de changelog manquante, vide ou **sans date** (vraie release seulement : l’essai à blanc passe avant de dater), une vraie release d’un commit absent de `main` (tag poussé ailleurs, ou lancement à la main depuis une autre branche), un lancement à la main dont le tag existe déjà sur un autre commit, et une release qui existe déjà ; le tag est posé sur le commit construit (`--target`). Actions épinglées par SHA (la version en commentaire : à monter ensemble), jeton du job hors de `.git/config` (`persist-credentials: false`), un avertissement de trimming fait échouer la publication. **Essai à blanc** : *Actions › Release › Run workflow* (case « dry-run » cochée par défaut) fait tout sauf créer la release et garde l'exe et les notes en artefact du run : à faire avant toute vraie release. Aucun secret : le jeton du run (`github.token`, droits *contents*, *id-token* et *attestations* en écriture pour ce seul job) suffit, la release étant dans le même dépôt. **Plus de publication à la main** (depuis la 1.6.1) : le README et les conditions d'utilisation promettent que chaque exe est construit par GitHub et attesté ; un exe compilé sur un PC n'aurait pas d'attestation. Si le workflow échoue, on le corrige et on relance, sans publier à la main.
- **Branches** (depuis la 1.6.1) : le travail se fait sur `dev`, gardée dans un dépôt privé avec tous ses commits ; `main`, publique, reçoit **un seul commit par release** (« Release X.Y.Z »), qui porte le tag. GitHub Actions est coupé sur le dépôt privé : la CI publique teste le commit de release, `dotnet test` en local teste le reste. À chaque release, depuis `dev` à jour et testée :
  ```
  git checkout main
  git merge --squash dev
  git commit -m "Release X.Y.Z"
  git push origin main          # CI, puis essai à blanc de release.yml
  git tag vX.Y.Z && git push origin vX.Y.Z
  git checkout dev
  git merge main                # indispensable : nouveau point commun, sinon le squash suivant rejoue les anciens changements
  git push
  ```
  La date du titre `## X.Y.Z — AAAA-MM-JJ` des deux changelogs se pose sur `dev` juste avant le squash.
- **Distribution** : un seul dépôt **public**, `Darvelize/game-radar` (code sous licence MIT, README, releases), depuis la 1.6.1. L'ancien dépôt des releases, `game-radar-releases`, a été renommé en `game-radar` : GitHub redirige l'ancien nom, ce qui garde la vérification des mises à jour des versions ≤ 1.6.0 (elles lisent encore `game-radar-releases`). **Ne jamais recréer un dépôt nommé `game-radar-releases`** : la redirection s'arrêterait. Nouvelle version :
  1. **Notes dans `CHANGELOG.md` et `CHANGELOG.en.md`** (sources uniques, embarquées dans l'appli pour la page « Nouveautés », choisies selon la langue) : section `## X.Y.Z — AAAA-MM-JJ` (date ajoutée à la publication), puis **deux parties** (choix de l'utilisateur, depuis la 1.2.0) : `### Évolutions` et `### Corrections` (en anglais `### Improvements`, `### Fixes`), une ligne `- ` par nouveauté, écrite pour les joueurs ; une partie vide est omise. `Changelog.Parse` les lit en `ChangelogEntry.Sections` (une version sans partie, les anciennes, a une seule partie sans titre), la page « Nouveautés » les affiche en intertitres (`ReleaseNotesSectionRow`), et l'extraction `awk` des notes de release les garde (`### ` ne correspond pas à `/^## /`) : GitHub en fait des intertitres. `The_running_version_has_release_notes` échoue si `<Version>` n'a pas sa section ; `TheEnglishChangelog_TranslatesEveryVersion` si l'anglais n'a pas les mêmes versions, dates, parties et nombres de lignes.
  2. Monter `<Version>`, `dotnet test`, commiter (commit « Release X.Y.Z »), publier. **Un numéro ne redescend jamais une fois diffusé** (l'avertissement de mise à jour compare les numéros).
  3. (Fait par `release.yml`, détaillé pour le comprendre ; jamais à la main, voir plus haut.) Notes de la release, **en français puis en anglais** = les sections extraites (`awk '/^## X\.Y\.Z/{f=1;next} /^## /{f=0} f' CHANGELOG.md`, idem `CHANGELOG.en.md`) + installation (remplacer l'ancien exe, SmartScreen) + SHA-256 (`Get-FileHash`), puis `gh release create vX.Y.Z "publish/GameRadar.exe#GameRadar.exe (Windows 64 bits)" --repo Darvelize/game-radar --title "GameRadar X.Y.Z" --notes-file <notes.md>`. `gh` installé par winget (`C:\Program Files\GitHub CLI\gh.exe`), connecté au compte Darvelize. Lien à partager : https://github.com/Darvelize/game-radar/releases/latest
  4. **VirusTotal** : `release.yml` envoie l'exe à VirusTotal (API v3) avant de créer la release. Les notes pointent vers son analyse par SHA-256, et le README la promet. Il faut le secret de dépôt `VIRUSTOTAL_API_KEY` (clé gratuite d'un compte virustotal.com, *API key* dans le profil). Sans ce secret, ou si VirusTotal échoue, la release part quand même avec un avertissement dans le run : envoyer alors l'exe à la main sur [virustotal.com](https://www.virustotal.com/gui/home/upload), sinon le lien affiche « introuvable ».
- Signature de code (étudiée en sept. 2026) : **pas rentable ici**. Azure Artifact Signing (~10 $/mois) n'est pas ouvert aux particuliers de l'UE ; un certificat OV coûte 150–300 $/an plus une clé matérielle ; depuis 2024, même un EV ne supprime plus l'avertissement tout de suite (la réputation SmartScreen se construit au fil des téléchargements, jamais atteinte avec un partage entre amis). Le Microsoft Store (gratuit, sans avertissement) ne convient pas à une appli qui repose sur des API non officielles.
- Non signé : au 1er lancement, Windows SmartScreen affiche « Windows a protégé votre ordinateur » → « Informations complémentaires » → « Exécuter quand même ». Windows uniquement (DPAPI pour les secrets). Chaque personne se connecte avec ses propres comptes ; ses données restent dans son `%LOCALAPPDATA%\GameRadar`.
